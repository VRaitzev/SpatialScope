# SpatialScope — подробное описание проекта

## 1. Общее назначение проекта

`SpatialScope` — это веб-платформа для анализа данных пространственной транскриптомики и whole-slide imaging (WSI), ориентированная на работу с данными формата Xenium. Система объединяет в одном приложении несколько уровней обработки:

- управление пользователями и ролевым доступом;
- управление проектами и наборами исследовательских данных;
- регистрацию мультимодальных Xenium-слайдов;
- просмотр метаданных и изображений whole-slide image;
- запуск инференса по выбранной области интереса (ROI);
- интерпретацию результатов работы моделей;
- сохранение и повторное открытие отчётов анализа;
- запуск фонового обучения пространственной модели;
- контроль текущего статуса обучающих задач;
- управление модельными пресетами.

С архитектурной точки зрения проект представляет собой интеграцию frontend-приложения на `Vue 3` и backend-сервиса на `FastAPI`, поверх которых реализован orchestration-слой, объединяющий файловые загрузчики, ML-модели, сервис интерпретации, training pipeline и persistence-слой на базе `SQLite` и `SQLAlchemy`.

Основная предметная идея системы заключается в том, что пользователь регистрирует Xenium-слайд, задавая три источника данных:

1. исходное WSI-изображение (`.tif` / `.ome.tif`);
2. табличное представление клеток и/или сегментационных координат (`.parquet`);
3. матрицу пространственной экспрессии (`.hdf5`).

После этого система позволяет работать с этим слайдом как с единым объектом: просматривать изображение, выделять ROI, запускать пространственный инференс, строить прогноз экспрессии генов, выполнять пост-хок интерпретацию результата и запускать переобучение пространственной модели на данных конкретного слайда.

## 2. Предметная область и практическая задача

Проект решает задачу поддержки анализа биомедицинских мультимодальных данных, в которых сочетаются:

- морфологическая информация из whole-slide image;
- сегментационные и клеточные структуры;
- пространственные транскриптомные данные;
- результаты машинного обучения и их интерпретация.

Практически система предназначена для сценария, в котором медицинский специалист, исследователь или администратор платформы должен иметь единый интерфейс для:

- загрузки и регистрации новых слайдов;
- доступа к уже зарегистрированным материалам;
- воспроизводимого запуска модельных конфигураций;
- анализа локального участка ткани;
- получения отчёта по прогнозируемой экспрессии;
- понимания вклада признаков и пространственной структуры в полученный результат;
- обучения и актуализации пространственной модели на собственных данных.

Таким образом, `SpatialScope` не является просто viewer'ом изображений и не является отдельным offline-ML-скриптом. Это именно прикладная аналитическая платформа, которая объединяет:

- слой пользовательского интерфейса;
- слой API;
- orchestration-логику;
- слой ML-моделей;
- слой persistence;
- слой интерпретируемости.

## 3. Архитектурный стиль системы

Проект построен по многослойной модульной архитектуре. В текущем коде можно выделить следующие логические уровни.

### 3.1. Presentation layer

Frontend-часть реализована как SPA-приложение на `Vue 3`, `Vue Router`, `Pinia`, `Axios`, `Tailwind CSS`, `OpenSeadragon`.

Этот слой отвечает за:

- отображение экранов входа и регистрации;
- навигацию между dashboard, viewer'ом слайда и отчётами;
- хранение токена и базовой пользовательской информации на клиенте;
- отправку HTTP-запросов на backend;
- ролевую адаптацию интерфейса;
- визуализацию результатов анализа и карт атрибуции;
- отображение WSI через `OpenSeadragon`.

### 3.2. API layer

Backend опубликован как `FastAPI`-приложение. Основной entry point — `backend/app/main.py`.

API-слой отвечает за:

- маршрутизацию HTTP-запросов;
- валидацию request DTO через `Pydantic`;
- аутентификацию по JWT;
- авторизацию по ролям через `require_roles(...)`;
- преобразование входных данных к формату orchestration-слоя;
- возврат JSON-ответов и выдачу файлов изображений.

### 3.3. Orchestration layer

Ключевой прикладной координатор системы — класс `XeniumSystemOrchestrator`.

Именно он связывает:

- загрузчики входных данных;
- реестр пресетов моделей;
- запуск экспертов и пространственной модели;
- интерпретацию;
- training pipeline;
- кэш слайдов;
- журнал фоновых задач;
- взаимодействие с БД.

Можно считать, что оркестратор является главным прикладным сервисом системы и реализует практически все основные бизнес-сценарии.

### 3.4. Model registry layer

Компонент `ModelPresetRegistry` хранит:

- доступные expert-модели;
- доступные spatial-модели;
- пресеты, связывающие их в готовые рабочие конфигурации;
- активный пресет по умолчанию.

Это позволяет пользователю работать не с отдельными нейросетями, а с готовыми модельными наборами.

### 3.5. Data access / persistence layer

Persistence-слой построен на `SQLAlchemy` и реализован через класс `DatabaseService` и ORM-схемы из `backend/app/core/data_managers/schemes.py`.

Он отвечает за:

- создание и поиск пользователей;
- создание и выдачу проектов;
- регистрацию слайдов;
- обновление статуса слайда;
- сохранение отчётов анализа;
- получение списка отчётов и конкретных отчётов;
- логирование действий в `AuditLog`.

### 3.6. ML / data processing layer

Этот слой состоит из следующих типов компонентов:

- загрузчики WSI и транскриптомных данных;
- адаптер загрузки границ клеток;
- expert-модели первого уровня;
- spatial-модель второго уровня;
- графовый dataset builder;
- pipeline обучения;
- интерпретаторы моделей.

## 5. Роли пользователей и модель доступа

В системе реализованы три основные роли:

- `clinician`;
- `researcher`;
- `admin`.

### 5.1. Clinician

Роль ориентирована на прикладной и диагностический сценарий работы. Пользователь с этой ролью может:

- входить в систему;
- получать свой профиль;
- просматривать проекты, к которым он имеет доступ через dashboard-данные;
- просматривать метаданные слайдов;
- открывать изображение слайда;
- запускать инференс по ROI;
- просматривать список отчётов;
- открывать конкретный отчёт;
- интерпретировать отчёт;
- экспортировать отчёт в JSON;
- получать статус задач обучения.

При этом `clinician` не может:

- создавать проекты;
- регистрировать новые слайды;
- запускать обучение;
- активировать пресеты.

### 5.2. Researcher

Роль исследователя ориентирована на подготовку данных и экспериментальную работу с моделями. Пользователь может:

- выполнять все базовые действия доступа и просмотра;
- создавать проекты;
- регистрировать Xenium-слайды;
- запускать инференс;
- запускать обучение пространственной модели;
- отслеживать статус фоновой training-задачи;
- работать с отчётами.

### 5.3. Administrator

Роль администратора предоставляет самый высокий уровень доступа. Пользователь может:

- выполнять все действия, доступные исследователю и врачу на уровне API-политик;
- активировать пресеты моделей;
- управлять пользователями через сценарий регистрации;
- выполнять обучение и запускать инференс;
- создавать проекты и регистрировать слайды.

### 5.4. Реализация авторизации

Авторизация реализована на backend через два механизма:

1. `get_current_user(...)` — декодирует JWT-токен и возвращает текущего пользователя;
2. `require_roles(...)` — ограничивает доступ к endpoint'у по роли.

JWT содержит:

- `sub` — идентификатор пользователя;
- `email`;
- `role`.

Пароли не хранятся в открытом виде. Для проверки используется `passlib` и `bcrypt`.

## 6. Структура данных и ключевые сущности БД

Основные ORM-сущности определены в `backend/app/core/data_managers/schemes.py`.

### 6.1. User

Таблица `users`.

Хранит:

- `id`;
- `email`;
- `name`;
- `password_hash`;
- `role`.

Связи:

- один пользователь владеет проектами;
- один пользователь связан с отчётами.

### 6.2. Project

Таблица `projects`.

Это контейнер верхнего уровня для исследовательской или клинической работы.

Содержит:

- `id`;
- `user_id`;
- `name`;
- `description`;
- `created_at`.

Связи:

- принадлежит пользователю;
- содержит множество `XeniumSlide`.

### 6.3. XeniumSlide

Таблица `xenium_slides`.

Представляет единый зарегистрированный мультимодальный слайд. Хранит:

- `id`;
- `project_id`;
- `patient_name`;
- `slide_tiff_path`;
- `cells_parquet_path`;
- `matrix_hdf5_path`;
- `slide_metadata`;
- `status`;
- `created_at`.

Статусы слайда в коде используются как минимум такие:

- `queued`;
- `processing`;
- `ready`;
- `failed`.

### 6.4. MLModel

Таблица `ml_models`.

Описывает атомарную ML-модель:

- имя;
- тип модели (`expert` или `spatial`);
- программный ключ;
- путь к весам;
- manifest-описание.

### 6.5. ModelPreset

Таблица `model_presets`.

Фиксирует готовую прикладную конфигурацию, объединяющую:

- expert-модель или набор expert-моделей;
- spatial-модель.

### 6.6. AnalysisReport

Таблица `analysis_reports`.

Это основной результат аналитического сценария. Отчёт хранит:

- `id`;
- `user_id`;
- `slide_id`;
- `preset_id`;
- `roi_coordinates`;
- `predicted_expression_data`;
- `created_at`.

Именно здесь сохраняются сериализованные результаты предсказания и интерпретации.

### 6.7. AuditLog

Таблица `audit_logs`.

Хранит критические события системы:

- кто выполнил действие;
- какое действие произошло;
- когда оно произошло;
- с какого IP-адреса было выполнено.

## 7. Основные backend-компоненты

## 7.1. DatabaseService

Файл: `backend/app/core/data_managers/ORM_manager.py`

Это прикладной сервис доступа к БД. Он инкапсулирует CRUD-операции и управляет жизненным циклом SQLAlchemy-сессии.

Основные функции:

- `create_user`, `get_user_by_email`, `get_user_by_id`;
- `create_project`, `get_project_by_id`, `get_user_projects`, `delete_project`;
- `register_xenium_slide`, `get_slide_by_id`, `get_project_slides`, `update_slide_status`;
- `register_ml_model`, `create_model_preset`, `get_all_presets`, `get_preset_by_id`;
- `create_analysis_report`, `get_report_by_id`, `get_slide_reports`;
- `log_action`.

Особенность реализации: используется обёртка `_execute(...)`, которая:

- создаёт сессию;
- выполняет операцию;
- делает `expunge_all()`;
- коммитит транзакцию;
- откатывает изменения при ошибке;
- закрывает сессию.

## 7.2. ModelPresetRegistry

Файл: `backend/app/core/registry/ModelPresetRegistry.py`

Это in-memory реестр моделей и пресетов.

Он хранит:

- словарь expert-моделей;
- словарь spatial-моделей;
- словарь пресетов;
- идентификатор активного пресета.

Ключевые функции:

- `register_expert(...)`;
- `register_spatial_model(...)`;
- `create_preset(...)`;
- `set_active_preset(...)`;
- `get_preset(...)`;
- `get_models_for_preset(...)`;
- `get_active_models()`;
- `get_available_presets()`;
- `get_weights_path(...)`.

Если в пресете указано несколько expert-моделей, реестр создаёт `CompositeExpertAdapter`, объединяющий их в один composite expert.

## 7.3. InterpretationService

Файл: `backend/app/core/interpretability/InterpretationService.py`

Сервис интерпретации координирует вызов интерпретаторов моделей.

Логика следующая:

- получает пресет;
- определяет expert-модели, входящие в пресет;
- для `EfficientNetExpertAdapter` создаёт `EfficientNetInterpreter`;
- для spatial-модели создаёт `GNNInterpreter`;
- собирает список `InterpretationResult`.

Интерпретация в системе может выполняться:

- сразу после инференса;
- отдельно для уже сохранённого отчёта.

## 7.4. XeniumSystemOrchestrator

Файл: `backend/app/core/orchestrators/XeniumSystemOrchestrator.py`

Это центральный компонент всей прикладной логики.

Внутреннее состояние:

- `slides_cache` — кэш загруженных слайдов и их runtime-компонентов;
- `jobs_registry` — реестр фоновых задач обучения;
- `registry` — ссылка на `ModelPresetRegistry`;
- `db` — ссылка на `DatabaseService`;
- `interpretation_service` — сервис интерпретации.

Основные группы методов:

### Управление слайдами
- `register_and_cache_slide(...)`
- `_ensure_slide_is_cached(...)`
- `get_slide_metadata(...)`

### Вспомогательная обработка патча
- `_patch_tensor(...)`
- `_run_expert_on_patch(...)`
- `_process_patch(...)`
- `_resolve_preset_id(...)`

### Инференс
- `run_inference_and_save_report(...)`

### Обучение
- `_collect_training_registries(...)`
- `start_background_training(...)`
- `get_job_status(...)`

### Отчёты и интерпретация
- `interpret_report(...)`

### Работа с проектами и dashboard
- `create_new_project(...)`
- `get_dashboard_data(...)`

## 8. Инициализация системы и загрузка моделей

В `backend/app/main.py` при старте приложения происходит bootstrap системы.

### 8.1. Инициализация БД

Создаётся SQLAlchemy engine и таблицы через:

- `create_engine(...)`
- `Base.metadata.create_all(bind=engine)`

### 8.2. Инициализация сервисов

Создаются:

- `db_service = DatabaseService(...)`
- `registry = ModelPresetRegistry()`
- `orchestrator = XeniumSystemOrchestrator(...)`

### 8.3. Регистрация expert-моделей

Регистрируются как минимум три expert-компонента:

- `efficientnet`;
- `geometry`;
- `radiomics`.

### 8.4. Регистрация spatial-моделей

Регистрируются как минимум две GNN-конфигурации:

- `gnn_multi`;
- `gnn_radiomics`.

### 8.5. Создание пресетов

При инициализации создаются два пресета:

1. `preset_multi_expert_gnn`
   - experts: `efficientnet`, `geometry`, `radiomics`
   - spatial model: `gnn_multi`

2. `preset_radiomics_gnn`
   - experts: `radiomics`
   - spatial model: `gnn_radiomics`

По умолчанию активируется:

- `preset_multi_expert_gnn`

## 9. Обработка Xenium-слайда

Слайд в `SpatialScope` рассматривается не как один файл, а как связанный набор данных.

Для регистрации слайда нужны:

- `tiff_path` — путь к изображению WSI;
- `parquet_path` — путь к табличным клеточным данным;
- `hdf5_path` — путь к матрице экспрессии.

### 9.1. Проверка файлов

Оркестратор проверяет существование каждого файла. Если хотя бы одного нет, выбрасывается `FileNotFoundError`.

### 9.2. Создание runtime-загрузчиков

Для зарегистрированного слайда создаются:

- `XeniumGenePanelLoader`;
- `XeniumWSILoader`;
- `XeniumCellBoundaryAdapter`.

### 9.3. Чтение метаданных

Из WSI извлекаются метаданные:

- ширина;
- высота;
- staining;
- mpp.

### 9.4. Кэширование

После регистрации в `slides_cache` сохраняются:

- загрузчик WSI;
- загрузчик RNA;
- boundary adapter;
- метаданные;
- ORM-запись слайда.

Это нужно для того, чтобы не пересоздавать тяжёлые объекты при каждом запросе.

## 10. Логика инференса

Инференс реализуется через endpoint:

- `POST /api/inference/run`

### 10.1. Входные параметры

`InferenceRequest` содержит:

- `slide_id`;
- `x`, `y`;
- `patch_size`;
- `preset_id`;
- `inference_region`;
- `regional_spots`;
- `target_gene`;
- `include_interpretation`.

### 10.2. Выбор пресета

Если `preset_id` не передан, система использует активный пресет.

### 10.3. Подготовка ROI

Если передан `inference_region`, он преобразуется в `SlideRegion`, а координаты патча вычисляются через `iter_patch_coords(...)`.

Если список `regional_spots` не указан, создаётся один центральный pseudo-spot.

### 10.4. Обработка патча

Оркестратор:

1. извлекает регион WSI через `XeniumWSILoader`;
2. получает сегментацию клеток через `XeniumCellBoundaryAdapter`;
3. извлекает признаки клеток с помощью expert-модели;
4. формирует `WSICellFeatureRegistry`.

### 10.5. Пространственный прогноз

После построения registry вызывается spatial-модель:

- `predict_spatial_expression(...)`

Результатом является `RegionalPredictionOutput`.

### 10.6. Интерпретация

Если `include_interpretation = true`, вызывается `InterpretationService`, который строит список интерпретаций для expert- и GNN-компонентов.

### 10.7. Сохранение отчёта

Результат сериализуется и сохраняется в `AnalysisReport`.

Дополнительно в `AuditLog` пишется событие вида:

- `RUN_INFERENCE | Preset: ... | Report: ...`

### 10.8. Возвращаемый результат

API возвращает:

- `status`;
- `report_id`;
- `preset_id`;
- `created_at`;
- `data`;
- `interpretation`.

## 11. Логика обучения

Обучение вызывается через:

- `POST /api/training/start`

### 11.1. Назначение

Этот сценарий используется для дообучения пространственной модели на данных конкретного слайда и выбранной области ткани.

### 11.2. Входные параметры

`TrainingRequest` содержит:

- `slide_id`;
- `preset_id`;
- `epochs`;
- `patch_size`;
- `max_patches`;
- `training_region`.

### 11.3. Подготовка training job

При старте обучения:

- вычисляется или выбирается пресет;
- кэшируется слайд;
- формируется training region;
- создаётся `job_id`;
- в `jobs_registry` добавляется запись со статусом `running`;
- статус слайда меняется на `processing`;
- событие записывается в `AuditLog`.

### 11.4. Фоновый поток

Обучение запускается в отдельном `threading.Thread(..., daemon=True)`.

Внутри worker'а:

1. собираются registry-объекты по множеству patch-координат;
2. извлекаются gene names;
3. строится `XeniumGraphDataset`;
4. создаётся `SpatialTrainPipeline`;
5. выполняется обучение `train(epochs=...)`;
6. загружается лучшая модель;
7. веса сохраняются в директорию checkpoint'ов;
8. spatial-модель обновляется лучшими весами.

### 11.5. Обновление статуса

При успехе:

- `jobs_registry[job_id][status] = success`;
- обновляется `loss`;
- фиксируется количество обученных графов;
- слайд переводится в `ready`.

При ошибке:

- статус job меняется на `failed`;
- в реестр записываются ошибка и traceback;
- слайд переводится в `failed`.

### 11.6. Получение статуса

Статус job доступен через:

- `GET /api/training/status/{job_id}`

## 17. Логика пользовательских сценариев

Ниже кратко собраны основные сквозные сценарии системы.

### 17.1. Вход в систему

1. Пользователь вводит email и пароль.
2. Frontend отправляет `POST /api/users/login`.
3. Backend находит пользователя, проверяет пароль и создаёт JWT.
4. Frontend сохраняет токен и профиль пользователя.
5. Пользователь попадает на dashboard.

### 17.2. Создание проекта

1. Исследователь или администратор вводит имя и описание.
2. Frontend отправляет `POST /api/projects`.
3. Оркестратор создаёт проект.
4. Событие логируется.
5. Новый проект появляется на dashboard.

### 17.3. Регистрация Xenium-слайда

1. Пользователь указывает пути к TIFF, Parquet, HDF5.
2. Backend проверяет существование файлов.
3. Создаются загрузчики и извлекаются метаданные.
4. Запись слайда сохраняется в БД.
5. Runtime-объекты помещаются в `slides_cache`.

### 17.4. Просмотр слайда

1. Frontend получает метаданные слайда.
2. Затем отдельно запрашивает TIFF-изображение.
3. OpenSeadragon визуализирует WSI.
4. Пользователь готовит ROI для анализа.

### 17.5. Инференс

1. Пользователь задаёт ROI, patch size, пресет, gene.
2. Выполняется извлечение патча.
3. Выполняется сегментация/чтение клеток.
4. Строятся клеточные признаки.
5. Пространственная модель строит прогноз.
6. При необходимости запускается интерпретация.
7. Результат сохраняется в виде отчёта.
8. Пользователь переходит на страницу результатов.

### 17.6. Обучение

1. Пользователь задаёт training ROI и гиперпараметры.
2. Backend создаёт background job.
3. Worker собирает training patches.
4. Строится графовый dataset.
5. Выполняется обучение GNN.
6. Лучшая модель сохраняется.
7. Статус job становится `success` или `failed`.

### 17.7. Работа с отчётом

1. Пользователь открывает список отчётов по слайду.
2. Выбирает нужный отчёт.
3. Просматривает predicted expression.
4. При необходимости запускает интерпретацию.
5. При необходимости экспортирует JSON.

## 20. Текущие ограничения и особенности реализации

Ниже перечислены не «ошибки», а важные особенности текущего состояния проекта, которые нужно учитывать при передаче описания другому агенту или при оформлении документации.

### 20.1. Часть конфигурации реестра моделей хранится in-memory

`ModelPresetRegistry` работает в памяти приложения. Это удобно для текущего runtime, но означает, что активный пресет и регистрация моделей не живут независимо от процесса без дополнительной persistence-обвязки.

### 20.2. Регистрация пользователей сейчас открыта endpoint'ом

В `backend/app/main.py` endpoint `POST /api/users/register` не ограничен `require_roles("admin")`. Это значит, что фактическая бизнес-политика в коде сейчас либеральнее, чем UI-описание роли администратора.

### 20.3. Background training реализован на `threading`

Это рабочее решение для локальной или исследовательской конфигурации, но не полноценная distributed job queue.

### 20.4. Система хранит пути к данным, а не сами бинарные объекты

В БД фиксируются пути к TIFF/Parquet/HDF5. Следовательно, целостность работы зависит от корректности локального файлового окружения.

### 20.5. Часть классов существует в кодовой базе как альтернативные или вспомогательные

В проекте присутствуют дополнительные загрузчики и адаптеры, например:

- `VisiumWSILoader`
- `ScanpySpatialTranscriptomicsLoader`
- `DinoV2ExpertAdapter`
- `CompositeExpertAdapter`

Однако в основных пользовательских сценариях текущей реализации ядро системы опирается на Xenium-ориентированный pipeline.

## 22. Краткое итоговое резюме проекта

`SpatialScope` — это role-based веб-платформа для работы с данными пространственной транскриптомики и whole-slide image, реализующая полный прикладной цикл:

- пользователь входит в систему;
- создаёт проект;
- регистрирует Xenium-слайд;
- просматривает метаданные и изображение;
- запускает инференс по ROI;
- получает предсказание экспрессии и интерпретацию;
- сохраняет отчёт;
- при необходимости запускает обучение пространственной модели;
- отслеживает результат и повторно использует обновлённые веса.

С архитектурной точки зрения система сочетает:

- современный SPA frontend;
- REST API на FastAPI;
- orchestration-слой, координирующий ML-пайплайн;
- реестр пресетов моделей;
- persistence-слой на SQLAlchemy;
- интерпретируемость и отчётность.

Если этот документ будет использоваться другим AI-агентом, его можно рассматривать как техническое и архитектурное описание текущей рабочей версии проекта, построенное по фактическому коду, а не по абстрактной концепции.
